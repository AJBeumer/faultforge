## Reuse

- **The config object itself.** `vitest.config.ts` is a plain `defineConfig({...})` default export (`vitest.config.ts:23`). A test can import it and read `test.projects[i].test.name`, `.include` and `.exclude` without any helper. Note the import side effect: the module calls `mkdtempSync` and registers `process.on("exit", ...)` at load (`vitest.config.ts:14-15`), so each worker that imports it creates one extra scratch folder, removed on exit. Harmless, but the test should say so.
- **The existing config-regression precedent.** `describe("vitest.config: temp directory isolation (#110)")` in `packages/harness/src/factory-tick.test.ts:1086-1097` is the one prior test that guards a `vitest.config.ts` setting. Its placement (inside an already-collected unit file, not a new root file) and its reasoning are the pattern to copy; see Alternative approaches.
- **The real list of files on disk.** The three integration tests under `packages/harness/test/` and the 24 unit tests under `packages/harness/src/` and `.claude/hooks/` (from `find --glob "**/*.test.ts"`) are concrete fixtures: assert that every path under `packages/*/test/` is selected by `integration` and not by `unit`, and every path under `packages/*/src/` and `.claude/hooks/` by `unit` and not by `integration`.
- **The factory's own test-file rule.** `factory.json:10` already encodes `^packages/[^/]+/test/` as a test-path pattern for `revert:check`; the new test's expectations should agree with it rather than invent a third notion of "integration path".

## Alternative approaches

1. **Put the test in a collected unit file, not a new root file (recommended).** Either a new `packages/harness/src/vitest-projects.test.ts` (matched by `packages/**/*.test.ts`, by `tsconfig.json:13`, and by `factory.json:10`'s `\.test\.ts$`) or a new `describe` block next to the existing `vitest.config: temp directory isolation (#110)` block in `factory-tick.test.ts:1086`. The project history chose the latter for the same reason (`1f247d1`), though `factory-tick.test.ts` is already 1714 lines and the config check has nothing to do with factory-tick, so a small dedicated file is cleaner. Either way the Notes line "Extend the existing `vitest.config.test.ts` at the repository root" must be replaced.

2. **Assert effective selection, not the include string.** Because the unit include does match `packages/harness/test/*` and only the exclude removes it (`vitest.config.ts:30-31`), the test must compute "matches include and not exclude" for each real file path. Options, in order of fidelity:
   - Run Vitest's own collection (`vitest list --project unit` and `--project integration`, or the JSON reporter) in a child process and compare the collected sets. This proves what `npm test` actually runs, but it spawns a process and takes seconds, which under `CLAUDE.md:79` belongs in `packages/*/test/`, where `check` never runs it. That defeats the purpose unless the owner accepts a slower unit test.
   - Import the config and match with `path.matchesGlob` from `node:path` (`engines.node >= 22` in `package.json`; availability and stability of `matchesGlob` on the project's Node version is an assumption, not verified here). No new dependency, so `revert:check` can still judge the PR.
   - Add a glob library: ruled out, because a dependency change makes `revert:check` exit 2 (`revert-check.ts:11-15`).

3. **Consider tightening the unit include so the criterion becomes literally true.** If the unit include were `packages/*/src/**/*.test.ts` and `.claude/**/*.test.ts`, the exclude would be redundant and "the unit include matches nothing under `packages/*/test/`" would hold as worded. Every unit test today sits under `packages/harness/src/` or `.claude/hooks/` (`find --glob "**/*.test.ts"`), so nothing would be dropped. This also gives the PR a code change for `revert:check` to revert, turning a test-only PR into one the factory can judge. It is a design decision for the owner (see Open questions), not something the ticket asks for.

## Open questions

1. Where does the test live: a new `packages/harness/src/vitest-projects.test.ts`, or a block in `factory-tick.test.ts` next to the #110 check? (The ticket's root-file location is not viable without widening the include.)
2. Which matching mechanism: Vitest's own collection in a child process (highest fidelity, slower, arguably an integration test by the layout rule) or `path.matchesGlob` on an imported config (fast, no dependency, assumes Node's matcher agrees with Vitest's)?
3. Should the first Done-when criterion be reworded from "include pattern matches no file" to "effective selection (include minus exclude) contains no file", or should the unit include be tightened to `packages/*/src/**/*.test.ts` so the criterion is literally true?
4. Is a test-only PR acceptable given `revert:check` will exit 2 ("can't judge")? If not, the ticket needs a code change (option 3 above) so the factory can prove the test fails without it.
5. Must the test also cover `.claude/**/*.test.ts` (five hook tests) and state that `vitest.proof.config.ts` is out of scope?
6. Should `packages/harness/test/README.md:7` ("The folder is empty until the first such test lands") be corrected in the same PR, now that three tests exist? It is out of the ticket's scope as written.
