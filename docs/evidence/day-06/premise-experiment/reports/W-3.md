## Reuse

- **The section list in `factory.json`** (`factory.json:12-14`). Adding `"Premises"` to `repos.faultforge.tickets.sections` is the whole change needed for `ticket:ready` to report `missing section "Premises"`. That is the design chosen in commit `83a1493` ("Describe both repos in factory.json … a third repo needs only a new entry") and `schemas/factory.v1.json:56-64` already allows any unique string in `sections`.
- **`readinessProblems` / `sectionsOf` / `isEmpty`** (`ticket-ready.ts:19-31, :48-62`). They already handle a missing heading, GitHub's `_No response_`, the form's untouched `- ` placeholder (`:30`), headings inside code blocks (`:20`), and case-insensitive heading names (`:23`). No new parsing code is needed.
- **`ticketReadyReport`** (`ticket-ready.ts:96-115`) and its exit codes (0 ready, 1 not ready, 2 could not read; commit `96b8c40`, closes #114) stay as they are.
- **Test pattern** in `ticket-ready.test.ts:28-31` ("names a missing Must not break section") is the template for a "names a missing Premises section" test.
- **Form pattern** in `task.yml:20-28` (`Must not break`: label, description, `value: |` with `-`, `required: true`) is the template for the new textarea.

## Alternative approaches

The Notes propose extending a `ticket-schema.json` with ajv. That file does not exist and tickets are not schema-validated, so the Notes cannot be followed as written. The implementation that fits the code is smaller than the ticket assumes:

1. Append `"Premises"` to `repos.faultforge.tickets.sections` in `factory.json`. `ticket:ready`, `/work-ticket` and the factory runner all read that list, so all three pick it up with no TypeScript change (`ticket-ready.ts:52-55`, `factory-tick.ts:1432`).
2. Add the textarea to `task.yml` with `value: |\n  -` so an untouched form reads as empty (`ticket-ready.ts:30`) rather than ready.
3. Update the test fixture and add one test for the new message.

Introducing a JSON schema for ticket bodies would be a new validation path for markdown prose, duplicating `sectionsOf`, and would go against the "one config file, data not code" decision of commit `83a1493`. Not recommended.

A note on done-when item 3: GitHub enforces `required: true` only in the web form; `gh issue create` and API edits bypass it. The real gate is `ticket:ready`, which is why item 2 matters more than the form flag.
