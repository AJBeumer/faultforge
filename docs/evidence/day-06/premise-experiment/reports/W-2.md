## Reuse

- **`privateDir(env?: NodeJS.ProcessEnv): string`** in `packages/harness/src/templates.ts:14-17` is the resolver. It already takes `env` as a parameter, so the new script calls `privateDir()` and its tests call `privateDir({})`, `privateDir({ FAULTFORGE_PRIVATE_DIR: dir })` without touching `process.env`. Importing it is the whole "resolve exactly as inject does" criterion, by construction.
- **Script-vs-import guard** at `ledger-check.ts:130-131`: `if (process.argv[1] && fileURLToPath(import.meta.url) === resolve(process.argv[1])) main();` lets tests import the module without running it. Use the same guard.
- **`main()` shape with one exit per meaning** at `ledger-check.ts:113-128` (`[ledger:check]` prefix on messages, `process.exit(2)` for "could not read", `0` for success) is the house pattern to copy for `[private:where]`.
- **Test fixture pattern** at `templates.test.ts:25-32` (`mkdtempSync` under `tmpdir()`, env object passed in) and the "no-such-private" idiom at `templates.test.ts:13`. `vitest.config.ts:25` gives every run its own `TMPDIR`, so temp fixtures need no extra cleanup.
- **Existing exit-code header text** to mirror: `ledger-check.ts:11-12`, `inject.ts:17-19`.

## Affected

- `package.json:5-23` gains one line, `"private:where": "tsx packages/harness/src/private-where.ts"`, matching the other `tsx packages/harness/src/<name>.ts` entries.
- New `packages/harness/src/private-where.ts` and `private-where.test.ts`. The unit project's include `packages/**/*.test.ts` (`vitest.config.ts:30`) picks the test up automatically, so it runs in `npm test` and `npm run check` (`package.json:13,15`).

The module header at `templates.ts:1-5` says it is "Shared by inject.ts ... and match.ts"; that sentence is already stale (ledger-check uses it too) and could name the new caller.
- Open ticket #108 (body in `docs/evidence/day-06/raw/triage-open-issues.json:62`) plans a `packages/harness/src/paths.ts` that "resolves the repo root, the private directory (`FAULTFORGE_PRIVATE_DIR`, else the parent of `factory.json`'s evidence folder) and the evidence and runs directories in one place", used by `inject`, `rules-evidence`, `rules-propose`, `factory-tick` and `factory-timeline`. Whatever `private:where` prints must follow that module when #108 lands, so the script should depend on the one exported function, not on its own copy.
- Not affected, but worth knowing: `factory-tick.ts:1384,1466` and `rules-propose.ts:173` would still disagree with `private:where` under a non-default `FAULTFORGE_PRIVATE_DIR` until #108 is done.

## Alternative approaches

1. **Import, don't copy (recommended).** The Notes say to copy the resolver line. That line no longer exists in `inject.ts` (`inject.ts:68` calls `privateDir()`), and copying it would create exactly the duplication CLAUDE.md:80 forbids and #108 is meant to remove. The script should be about 15 lines: import `privateDir` from `./templates.ts`, `existsSync`, print, exit. "The two can never disagree" is then true by construction, and the test for it is trivial.
2. **Rename the "exactly as inject does" criterion** to "exactly as `privateDir()` in `templates.ts` does", so the Done-when stays checkable after #108 moves the function to `paths.ts`.
3. **Narrow the Result wording.** "The private folder the harness will use" overstates it: `factory:tick` and `rules:propose` compute their own path (`factory-tick.ts:1384,1466`, `rules-propose.ts:173`). Either say "the private folder `inject`, `match`, `verdict`, `case:build` and `ledger:check` will use", or make this ticket depend on #108.
4. **Consider a flag instead of a script.** `inject.ts` already parses `--validate-only` (`inject.ts:10-15,70-75`); a `--where` flag would be smaller than a new script and package.json entry. Against it: inject's header is already dense, and a separate script keeps "print the path only; never list the folder's contents" easy to audit. The ticket's choice (new script) is defensible; this is noted only as the smaller option.
5. **Print to stdout, reason to stderr.** On a missing folder, still print the resolved path (that is the whole point: the owner wants to see which path was tried) and put the "does not exist" message on stderr with exit 2, the way `ledger-check.ts:118-119` separates its messages. The ticket does not say whether the path is printed on the failure path.
