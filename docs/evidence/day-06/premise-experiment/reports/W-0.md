## Reuse

- `sectionsOf()` (`packages/harness/src/ticket-ready.ts:18-26`): already strips fenced code blocks and returns each `###` section's trimmed text keyed by lower-case name. The change should keep calling it and only post-process the returned text.
- The existing number regex `/(?<![\w/-])#(\d+)\b/g` (`ticket-ready.ts:36`): its lookbehind already excludes `owner/repo#3` and `word#3` forms, which is why "target 3" and cross-repo mentions never counted. Keep it unchanged; only narrow the text it runs over.
- `isEmpty()` (`ticket-ready.ts:28-31`) is the house pattern for "text that means nothing"; a "None" recogniser belongs beside it.
- `checkTicket()` (`ticket-ready.ts:71-89`) filters written numbers by live state and merges them with native `blocked_by` links. No change needed there.
- Test fixture `ready` (`ticket-ready.test.ts:11-21`) and the existing `${ready}\n\n### Depends on\n...` shape (`:75`) are the input template for the three new cases.
- Blame shows `writtenDependencies`, `sectionsOf` and `isEmpty` all came in one commit, `c28c4262` "Readiness check: written blockers, placeholders, code blocks, every page" (2026-11-06T18:27:54Z), the follow-up to `2169642b` "refuse tickets that aren't ready" (ticket #47, PR #53 per `docs/decision-log.md:61`). That commit's tests under `describe("review findings on PR 53")` are the precedent for adding edge cases one by one.

## Alternative approaches

The ticket's "first non-empty line only" rule fixes a symptom but is underspecified in two places and moves the failure mode to the unsafe side.

1. Same-line note. If #4's text is `None. (#108 may later move this)` on one line, the first-line rule still returns `[108]` and the reported case stays broken. The "Why" does not say which it was.
2. Multi-line lists. Nothing enforces one line; the day-6 snapshot shows every Depends on value on one line (`triage-open-issues.json`, e.g. `#64, #67`, `#42, #43, #37`), but a future `#12\n#15` would silently drop #15 and report the ticket ready. Today's bug errs toward "blocked" (the owner fixes the ticket, `factory/SKILL.md:16`); the proposed rule errs toward "ready".
3. "Note before the list" (the ticket's own third test case) contradicts the rule: the first line would be the note, which contains `#108`, so the real list on line two is never read.

Two narrower options that cover all three of the ticket's cases and the same-line variant:

- **A. Recognise "None".** If the section's first non-empty line, with trailing punctuation removed, is `none` (case-insensitive), return `[]` whatever follows. One line of code beside `isEmpty()`, and it exactly matches the reported failure. Still blocks on a note that follows a real list.
- **B. Drop parenthesised text** (`text.replace(/\([^)]*\)/g, "")`) before matching. Covers "(#108 may later move this)" on the same line or the next, and before or after a list, without changing how lists are read. Numbers in parentheses stop counting, which must be stated in the form.

Recommendation: A plus B, keep the whole-section scan otherwise. If the owner prefers the first-line rule, it should at least be "first paragraph" (stop at the first blank line) and still include A, and the form must say "issue numbers only, one line; notes go in Notes".

Zero-code alternative: change the ticket text convention only (form description) and move the note to Notes on #4. Cheapest, but the factory already stopped once on text a human reads as reasonable, so a parser fix is justified.
