## Day 1: Your factory's first delivery

- **Challenge requirement:** introduce the project, sign up for Qodo, build one small capability with a coding agent, open a focused PR, run a Qodo review, and share one lesson.
- **Increment delivered:** a small booking API with one invariant: sending the same request twice with the same idempotency key never creates two bookings. One injected bug bypasses the idempotency check, confirmed by a hidden test, and goes out as a normal-looking PR for Qodo to review. Recorded as case FF-0001.
- **What changed from the plan and why:** the injected bug is a one-line slip rather than a removed guard. On a repeat request, the code looks up the original booking by the idempotency key instead of the booking id it saved. Removing the whole guard would also have broken an existing public test, so the PR would have arrived with red CI and given the answer away. With this version, the target's own tests and typecheck still pass, and only the hidden proof test fails.
- **Tests and Qodo evidence:** [faultforge-target#1](https://github.com/AJBeumer/faultforge-target/pull/1), reviewed commit `c7ffd15`. Qodo's PR summary (14:27 UTC) and its code review (14:28 UTC) both flagged the bug. The review raised one finding, rated High, in `src/bookings/create.ts`, lines 24 to 61. It said a repeat request creates a second booking, and that a key equal to another user's booking id returns that user's booking. Under the fixed match rule, the right file, overlapping lines and the right kind of problem, **FF-0001 is detected**. I reproduced the second claim with a test: it holds.
- **Lesson or decision:** a one-line bug planted to break one rule actually broke two. Besides creating duplicate bookings (INV-IDEMP-001), it let one user read another user's booking (INV-AUTH-001). The answer key and the hidden test only knew about the first; Qodo found both. So the answer key has to record everything a planted bug breaks, not just what it was meant to break, or a reviewer's correct extra finding would be counted as noise.
- **Remaining risk:** Qodo's local structured review is not verified yet; that is the Day 2 gate. The finding's line range covers 38 lines, so "overlapping lines" is a loose test for wide ranges. The Qodo trial shows 14 days, not 30. GitHub also requested a Copilot review automatically. It posted after Qodo, so it didn't affect this case, but it has to be switched off for later ones.

### Decisions made today

- **Match rule fixed before any data.** A Qodo finding counts as a catch only if it names the injected file, overlaps the injected lines, and describes the right kind of problem. The rule is not loosened after seeing results.
- **Two repositories.** The harness lives here. The booking API lives in a separate target repository, so the answer key never sits next to the code Qodo reviews.
- **Neutral PRs.** Branch names, commit messages, and PR descriptions for injected bugs must read like ordinary changes.
- **Day 1 counts even if Qodo misses the bug.** A miss is an honest data point, not a failure.
- **The replay check is not in the target's own tests.** Repeat-request behaviour is checked only by the hidden proof test, so a planted bug there doesn't show up as a CI failure.
- **One reviewer per case.** Only Qodo reviews target PRs. Any other bot's output is saved but doesn't count. The two repositories are never linked in Qodo, so FaultForge's templates can't reach the review.
- **No force-pushes to the target's `main`.** Published history stays as it is. Cases record the exact commit that was reviewed.
- **Unreleased templates stay private.** This changes the charter's layout: a bug template and its proof test live in the private repository until their case is adjudicated, and only then may be copied to `templates/seed/`. Held-back benchmark templates never go public. The inject command looks in private storage first.
- **Rules enforced in code, not just in docs.** `CLAUDE.md` holds the rules for coding agents. A Claude Code hook blocks giveaway words in anything sent to the target repository and blocks force pushes to it. The inject command refuses giveaway branch names and commit messages. The `/new-case` and `/daily-challenge` skills hold the repeatable routines.
- **Qodo configuration v2 for every case after FF-0001.** FF-0001 ran on Qodo's default Precision preset (v1). Qodo's own data showed it had then linked this repository and the target by itself, and that it can mine its own review rules from past PRs and activate them without approval. Either would let earlier cases or the lab itself influence later reviews. v2 switches off three settings: the cross-repository review agent, rule mining from review history, and auto-approval of mined rules. Everything else stays on the Precision preset. FF-0001 isn't affected: its review used no cross-repository context and no rules existed. Before every case we now check through Qodo's API that the target has no linked repositories and that no rules exist.
- **One history rewrite in this repository, on Day 1.** The first commit's message had a `Co-Authored-By: Claude` line, which I removed so GitHub's contributor list matches who owns the project. Only that one line changed; files, authors and dates are the same. No case refers to this repository's commit ids. The target repository was not rewritten, so FF-0001's commits are unchanged. Claude Code is still the coding agent used to build this project.

## Day 2: House rules

- **Challenge requirement:** create an `AGENTS.md` at the repository root with a short project description, setup and verification commands, and three to five project rules, each saying where it applies and why it exists. Commit and push it, and check that Qodo has turned the rules into review standards.
- **Increment delivered:** an [`AGENTS.md`](https://github.com/AJBeumer/faultforge-target/blob/main/AGENTS.md) in faultforge-target, the repository Qodo reviews. Four rules: idempotency keys belong to a user; someone else's booking is "not found", never "forbidden"; check the whole request before touching the store; no real clock or random ids in application code. Merged through [faultforge-target#2](https://github.com/AJBeumer/faultforge-target/pull/2) (merge commit `841d69d`). Qodo imported the rules, and they are now part of the reviewer's configuration (v3).
- **What changed from the plan and why:** I expected four rules. Qodo made 18: 8 from `AGENTS.md`, which it split into finer rules, and 10 from `INVARIANTS.md`, which it imported as well. One rule, "do not double-book a resource", came from an invariant marked *not yet enforced*. The code doesn't enforce it, so it would flag existing behaviour on unrelated PRs. It was switched off. Qodo left another rule inactive by itself, because it overlaps an `AGENTS.md` rule. 16 rules are active. The same PR also fixed the target's `package.json` description, which named this project. That broke the target's no-mention rule, and it had been public since Day 1.
- **Tests and Qodo evidence:** target `npm run check` passed (typecheck, lint, 19 tests). Qodo reviewed PR #2 at commit `d96ac35` and found no issues (0 bugs, 0 rule violations, 0 requirement gaps). The rules were checked through Qodo's API after import: 18 rules, 16 active, no review skills, no linked repositories.
- **Lesson or decision:**
  - **Configuration v3 = v2 plus the rules imported from the target's `AGENTS.md` and `INVARIANTS.md`.** Every case from now on runs under v3. FF-0001 stays a v1 result. Before each case, `/new-case` compares Qodo's rules with the saved v3 snapshot and stops on any difference.
  - **Editing `AGENTS.md` or `INVARIANTS.md` in the target is now a configuration change.** Qodo keeps imported rules in sync on pushes, so a one-line doc edit changes the reviewer.
  - **A house rule written from a review can carry that review's answer.** One imported rule reads "fetch the original booking via the stored idempotency record's bookingId, never via the client key". That is the FF-0001 bug almost word for word. Re-running that bug under v3 would measure whether Qodo applies a rule, not whether it finds a bug unaided, so it can't serve as a before-and-after comparison.
- **Remaining risk:** the rules cover most of the target's invariants, so cases on those topics now test "Qodo plus house rules" rather than Qodo alone. That is how a real team would run it, but results must be reported with their configuration version. Qodo's structured review output (the charter's Day 2 gate) is still unverified, and is carried to Day 3.

The third time cost something: on [target PR 6](https://github.com/AJBeumer/faultforge-target/pull/6), Qodo created a finding a minute after "no open findings" and edited the comment five minutes later, after the PR had been called done. ## Day 4: Automate your factory's first job

- **Challenge requirement:** start the agent with a trigger (a schedule or a `ready-for-agent` label) without opening a session. The agent reads the ticket and the project rules, implements, runs the checks against the acceptance criteria, opens a PR for Qodo, fixes confirmed findings and repeats, with a retry limit, stopping for help when stuck. The owner decides on the merge. Try it and note the checks, reviews, retries and blockers.
- **Increment delivered:**
  - **The factory runs in GitHub Actions** ([`factory.yml`](../.github/workflows/factory.yml), [docs](factory-trigger.md)). The owner's `ready-for-agent` label on a ticket in this repo starts a run at once; a schedule every 15 minutes picks up target tickets. A cheap first job checks whether anything is labelled. One run takes one ticket, runs the `/factory` loop in headless Claude Code with a $25 budget, a 120-minute limit and at most three review rounds, and ends with `agent-done` or `agent-needs-help` and a comment saying why. It never merges. Keys are repo secrets; pushes use the owner's token, because Qodo ignores pushes by bots.
  - **It doesn't take the agent's word.** After the agent stops, the runner checks effects, not just commands: `main` of all three repos, the guardrail files, every comment, review and ticket change by the agent's login during the run, and a fresh snapshot of the ticket. Then it verifies the PR itself: a clean agent exit, green checks, and Qodo's review of the head commit complete with no action-required finding open.
  - **It trusts only the owner's text.** A ticket is refused unless the owner added the label and wrote, edited and commented every part of it (all pages, comment edits included). The agent works from a checked snapshot of the ticket; live reads of issues are blocked during a run.
  - **A policy hook for unattended runs** ([`factory-policy.ts`](../.claude/hooks/factory-policy.ts)), next to the guard hook: no merges, PR comments or Qodo replies, ticket labels, `gh api` writes, force pushes, pushes to `main`, environment reads, HTTP outside localhost, edits outside the run (following links) or under `.claude`. The runner refuses to start an agent unless both hooks are switched on in the workspace it gets from `main`.
  - **`factory:timeline`** prints a run's log as a table with a one-line summary. The factory built that summary itself (run 2 below).
  - Tickets [#63](https://github.com/AJBeumer/faultforge/issues/63), [#68](https://github.com/AJBeumer/faultforge/issues/68), [#70](https://github.com/AJBeumer/faultforge/issues/70) and [#74](https://github.com/AJBeumer/faultforge/issues/74), in PRs [#65](https://github.com/AJBeumer/faultforge/pull/65), [#69](https://github.com/AJBeumer/faultforge/pull/69), [#72](https://github.com/AJBeumer/faultforge/pull/72) and [#75](https://github.com/AJBeumer/faultforge/pull/75).

  - The fix loop has run unattended once, on one finding from a lite review.
  - `FACTORY_GH_TOKEN` is the owner's broad hackathon token. A narrower one (three repos; contents, issues and pull requests only) is still to be made.
  - Not yet seen live: a `workflow_dispatch` run, and a second trigger waiting behind a run in progress (#68).

## Day 5: Make your factory self-improve

- **Challenge requirement:** "Use Qodo or your coding agent to look back at the code and review feedback, find an expectation worth capturing, and propose a rule for future work. You'll check the evidence and refine the suggestion before deciding what belongs in your factory." Then save the rule via a PR, verify it in Qodo with the intended scope, and share the decision with its evidence (discussion 7).
- **Increment delivered:**
  - **An evidence table the proposals stand on** ([#77](https://github.com/AJBeumer/faultforge/issues/77), [PR #81](https://github.com/AJBeumer/faultforge/pull/81)): `rules:evidence` builds one deduplicated table from the saved reviews — finding, category, PR, first-seen commit, whether it was still open at the PR's last complete review — excluding case PRs by case record and answer key, failing closed when an exclusion source is unreadable. `--check` verifies any citation against the table.
  - **The factory proposes rules to itself** ([#78](https://github.com/AJBeumer/faultforge/issues/78), [PR #86](https://github.com/AJBeumer/faultforge/pull/86)): after each finished run, `rules:propose` groups the table by repo and category and opens a proposal ticket when a pattern crosses the fixed threshold (3 findings across 2 PRs), deduplicated by title. Live, it opened proposals [#82](https://github.com/AJBeumer/faultforge/issues/82)–[#85](https://github.com/AJBeumer/faultforge/issues/85); a second run opened nothing.
  - **The first house rule, adopted blind** ([#79](https://github.com/AJBeumer/faultforge/issues/79), [PR #91](https://github.com/AJBeumer/faultforge/pull/91)): a fresh agent session saw only the challenge prompt and the Day 3 slice of the table (24 findings) and proposed three candidates with citations; every citation passed `rules:evidence --check`. Scored against the 29 Day 4 findings it never saw, the winner named 3 clearly and 2 borderline; the rejected candidates scored 2+1 and 0, and stayed at their cheaper enforcement points (per-script tests, the runner's audit). The owner approved and merged the rule — "Evidence capture is fail-safe and complete" — into a new root `AGENTS.md`.
  - **Qodo configuration v6, recorded:** the portal import split the one rule into six clause-rules, faithfully, and turned its "Where it applies" line into the path scope `packages/harness/src/`. The import also auto-activated 16 rules it derived from `CLAUDE.md` and `docs/CHARTER.md` that never went through the adoption pipeline — among them its own rendering of the charter's "Do not activate proposed standards changes automatically". The owner toggled those two files off: v6 is exactly v5 plus the adopted rule. - **Lesson or decision:**
  - **A rule import is a configuration event, not a formality.** Qodo read three files where one was intended and activated 16 unadopted rules. Every future import gets the same treatment: snapshot, diff against the previous version, owner decision on anything unexpected.
  - **On this evidence, a house rule changes the verdict, not the catch.** Escalation and rule-linkage are what the rule buys; the catches were already there. Worth re-measuring when a rule covers something Qodo does not find on its own.
  - **The fail-safe discipline paid for itself on measurement day:** the first watcher launch ran without the API key, and `review:wait` exited without recording anything rather than writing an error as data. The relaunch cost four minutes and zero evidence.
  - **Qodo skips docs-only PRs** (`review_effort: skip` on #96). A skipped review is a recorded outcome, never a clean one; factory tickets must not be docs-only.
- **Remaining risk:**
  - The toggled-off `CLAUDE.md`/`CHARTER.md` rules are "In-repo" sources: a future import may re-derive or re-activate them. The v6 README says to check the active set against the snapshot at every configuration check.
  - The after-arm reviewed diffs the reviewer had seen before; its catches are not independent evidence (stated in the report).
  - One clause-rule ("read every page") was never linked to the finding it covers; per-clause linkage looks best-effort.
  - Four diffs measure a direction, not a rate.

### Decisions made on 9 November, after the Day 5 entry

- **Code layout, written down (#112).** Unit tests stay next to the code they test, as `<name>.test.ts`; slow and end-to-end tests get their own folder, `packages/<package>/test/`, and their own Vitest project, run by `npm run test:integration` and never by `check`. The owner asked whether a root `tests/` tree mirroring the source would be cleaner. Decision: no. In TypeScript with Vitest the colocated test moves with its file, imports stay short and a missing test shows in the folder listing; a mirrored tree duplicates every path and breaks on every move, and it would also change the `tests` pattern `revert:check` depends on. The rules are in `CLAUDE.md` under "Code layout", not in `AGENTS.md`, because Qodo imports `AGENTS.md` as review rules and that would be a new configuration version for a layout convention.

### Decisions made on 10 November

- **Factory token narrowed (10 November, #103).** The owner changed the permissions of the token behind `FACTORY_GH_TOKEN` on 10 November, keeping the same secret. Checked read-only through the API the same day: the token is fine-grained (it expires 5 January 2027); on the three repositories it reads contents, issues and pull requests; on the private repository, where a public repository's permissionless reads cannot mask a grant, it is refused Actions workflows and runs, environments, deployments, secrets and branch protection. The write side is proven by the first unattended run after the change, which the runner records in its log.

### Decisions made on 11 November

- **The runner publishes only evidence to the private repository (11 November, #102, [PR #141](https://github.com/AJBeumer/faultforge/pull/141)).** Before anything is staged, `saveEvidence` lists every path the run's private worktree changed against `origin/main`. If any of them is outside `raw-artifacts/` and `factory-log/`, nothing reaches `main`: the commits go to a `blocked-<run id>` branch instead, the ticket gets a needs-help comment naming the paths and the branch, and the run ends as needs-help. The answer key and the audit log stay the owner's to amend, by hand and by appending.
- **A workflow artifact is not a fallback for private evidence.** Qodo asked that a blocked run whose quarantine push fails should upload its log and transcript as a workflow artifact, so a discarded CI machine can't lose them. Declined: the factory workflow runs in a public repository, and anyone with a GitHub account can download a public repository's workflow artifacts, so that fallback would publish the private evidence. The push is retried three times; after that the run folder is the last copy and the ticket says so. A run that loses its evidence is reported, not covered up.
- **The agent's guardrails now cover the private repository's protected files (11 November, #142).** The policy hook denies an unattended run any edit in the private worktree to `ground-truth.jsonl`, `audit-events.jsonl`, `templates/` or `config/`; the evidence folders stay writable. This is a change to the hook's unit-tested behaviour, not to Qodo's configuration (still v6). It was made by hand in an interactive session, because the hook holds the agent's own guardrails and no unattended run may edit it. The diff check above is the guarantee; the hook is the first line, so the agent learns at the edit rather than at the end of the run that the file isn't its to change.
